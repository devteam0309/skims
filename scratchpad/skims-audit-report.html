01Summary

The audit found the foundations already in place and unused. barangay existed as a reference on User, Program, YouthMember, Expense and Document; Notification.priority existed; documents already soft-deleted; expenses already had a rejected status. Nothing read any of it. Most of this round is enforcement and workflow around structure that was already there, which is why it required no destructive schema change.

Every scope decision now runs through one module, backend/src/utils/scope.js. Municipality and barangay are resolved from req.user; a supplied ?barangay= can only narrow, never widen; a bound officer's create is pinned to their own barangay. A record with no barangay stays municipality-level and visible — every record written before this change has none, so treating "no barangay" as "not mine" would have blanked the Programs, Youth, Expenses and Documents pages for every officer on the day it shipped.

The aggregate views followed in a second pass: dashboard, monitoring, analytics and all three reports use the same helper, so a figure and the rows beneath it now describe the same set of records. Where a collection carries a barangay it narrows on one; budgets and liquidations do not and stay municipality-level, because SK money is drawn per municipality and fiscal year.

Applying it surfaced three live fail-open reads that were nothing to do with barangays: getDocumentStats had no role check at all and returned province-wide category counts plus the five most recent documents — with uploader names — to any authenticated account; deleteExpense had no scope check on a route open to municipal_admin, a municipality-scoped role; and the dashboard’s user count was province-wide for every role, so a Boac chairperson’s dashboard reported the province’s headcount as their own. All three are closed, all three have regression tests.

Four decisions you made before I started, and what they cost

Barangay scope narrows only where a barangay is recorded.

No invented data, no lock-outs, and existing accounts behave exactly as they did. The cost is that the isolation is only as real as the assignment work — until an account is assigned, it is municipality-wide, and the migration script reports rather than guesses.

SK Chairperson is view-only in Fund Management; approvals to the admin tiers.

This reverses September's arrangement, where the chairperson could both create and approve. The treasurer records money and approves nothing; the municipal administrator decides. Two existing tests encoded the old rule and were rewritten deliberately, not deleted.

Superadmin keeps full access.

Your brief allowed it where the architecture already requires it, and it does: super_admin is the break-glass account and the sole approver of registrations. The intent is honoured where it matters — User Management and Audit Logs remain super_admin only.

Both the programmes list and the milestone list become tables.

"Program parts" was ambiguous, so both readings were built: the Programs card grid is now a table with a target-barangay column, and Program Detail's milestone list is a table of parts with status, dates, progress and who is responsible.

The aggregate pass

dashboardController, monitoringController, routes/analytics.js and reportController each carried their own three-line municipality filter; all four now call applyReadScope. Three needed two filters rather than one, because a single filter across collections that do and do not carry a barangay either leaves half the figures municipality-wide or asks a collection for a field it has no column for — which matches nothing at all rather than narrowing.

Youth engagement gained a byBarangay breakdown and the Analytics page a chart for it: for an account inside one municipality the municipality chart is a single bar labelled with its own name, which says nothing, while the barangay split is the comparison that account can act on. Capped at the twelve largest with the remainder stated, because Boac alone has 61 barangays.

Two things were deliberately left municipality-level. /api/monitoring/municipalities prints one row per municipality, labelled with its name — a barangay figure under that heading would be a wrong number, not a narrower one. And /api/dashboard/municipality-comparison stays province-wide and money-free, by the earlier decision that made it safe to show an SK Chairperson at all.

Two fixes worth naming

Filters are built with real ObjectIds, not strings. find() casts a string id against the schema; an aggregation $match does not — the pipeline goes to the server as written, a string never equals an ObjectId, and the stage matches nothing. Every scoped stats and summary endpoint runs through an aggregation, so a filter built from string ids would have reported zero of everything to every scoped account. The document-stats test caught it.

toFormData appends arrays element-wise. fd.append(key, ['a','b']) stringifies to "a,b" — one field holding a comma-joined blob, which a handler expecting a list discards as the wrong type. The supporting-document links were silently dropped exactly that way until a frontend test caught it. The backend also coerces a single id, since multer only produces an array when the field repeats.

04Frontend changes

  • Public Portal is the landing page. / was the authenticated shell, so opening the system sent an anonymous visitor to a login form and the transparency portal was reachable only by knowing the /portal URL. The staff layout became a pathless route with absolute child paths, so every existing URL is unchanged — only / moved. /portal stays as an alias.
  • Programs list is a table with Municipality, Barangay, Status, Dates, Budget, Participants, Progress and Created-by columns, and a barangay filter whose options follow the municipality filter. Program Detail's milestones became a parts table.
  • Cancelling a programme has its own dialog — danger styling, plain wording, and "Keep the program" as the way out. The other four statuses keep the ordinary one.
  • The barangay picker is gone for an officer who has one, on both the Youth filter bar and the registration form. Their barangay is stated instead. A picker whose every selection the server discards is the failure this page already had twice with the municipality control.
  • Youth import wizard — template download, file choice, a row-by-row preview using the spreadsheet's own line numbers, then confirm. Invalid rows carry their reason; duplicates say which line they duplicate.
  • Expenses gained Return beside Approve, with the reason collected in the dialog rather than demanded by a 422 afterwards, and shown on the returned row. Submit and Save-as-draft belong to the author.
  • Documents gained a recycle-bin view with Restore and Delete-forever. The delete dialog no longer claims the document "will be permanently deleted" — it never was, and now it demonstrably is not.
  • Email changes are requested from the profile and decided in User Management, where the queue shows both addresses. Barangay assignment sits beside the role change.
  • Announcements moved beside Notifications in the sidebar. Same role list, same guards; it had been filed next to the audit trail.
  • Notifications state their own order — "Most urgent first, then most recent" — because the list is deliberately no longer chronological.
  • The Dashboard names the barangay and says what the figures cover, including that budget and liquidation totals remain the municipality’s. The numbers changed meaning in this round, and a number whose scope changed silently is a number read wrongly.

06Security changes

  • Two fail-open reads closed — getDocumentStats (no role check at all) and deleteExpense (no scope check on an ADMINS route that includes a scoped role).
  • Barangay cannot be set from a request. ?barangay=, a body field and a hidden input are all ignored for a bound account, and a linked programme or supporting document is re-checked against the caller's own scope before it is stored.
  • Every scoped filter fails closed to { $in: [] } rather than relying on Mongoose treating an undefined value as null.
  • Creating and approving are separated by role, not only by the self-approval guard — which only ever stopped an officer approving their own expense, leaving one treasurer free to approve another's.
  • An email change cannot be applied without review, and requires the current password: the address is the login identifier and the password-reset destination, so an unreviewed change is an account takeover by typo or borrowed session.
  • The audit trail has no write route — the router mounts a single GET, super_admin only, asserted by test rather than trusted as a fact about the file.
  • The youth deny-by-default allowlist covers all new endpoints without anyone having to remember to add them; asserted for the import, the recycle bin and the email queue.

07Data migration

backend/scripts/migrate-barangay-scope.js reports; it does not guess. No SK account has ever had a barangay, and there is no fact in the database from which the right one can be derived — an email domain names a municipality at best, and Barangay.skChairperson is unpopulated too. Guessing would confine a real officer to the wrong barangay, where they would see a roster that looks complete and is not.

Dry-run by default. --apply writes only what an explicit email → barangay mapping names, each resolved within that user's own municipality so a name that exists in two municipalities cannot be mis-assigned. Everything else is listed as a migration exception.

  • Records are not back-filled. A programme, youth member, expense or document with no barangay is a municipality-level record and stays readable by the whole municipality.
  • No re-seed is required for any of this to work. The seeder was updated so the feature is visible in a demo: Boac's chairperson and treasurer are put in different barangays and Boac's ten youth are split between them, so each opens a registry with five members — spread over 61 barangays they would have seen one each and read the scope as a broken filter. Santa Cruz's chairperson and Gasan's secretary are left unassigned on purpose, because that is the state every real account is in and it has to keep working.
  • Still true from before: local development writes to the shared Atlas cluster, and npm run seed is unguarded there. Nothing in this round was run against it.

09Remaining issues

  • Analytics and Reports have no barangay filter of their own. The figures are correctly scoped and a province-wide reader can still narrow by municipality, but there is no control to pick one barangay out of a municipality the way Programs and Youth now have. The endpoints already accept ?barangay=; this is UI only.
  • Multi-barangay programmes are not supported. Program.barangay is a single reference; "no barangay" means municipality-wide. Your brief made this conditional on the system already supporting several, and it does not — an array would change the scope query, the filter and the column. Say the word if a programme needs to name three barangays.
  • Notification levels are low / medium / high / urgent, not your "Normal". The existing values are used by roughly twenty call sites and your brief said to prefer the project's conventions; renaming is a data migration for a synonym.
  • Expense draft is reachable only through the new Save-as-draft control. The default remains pending so nothing already recorded changed meaning — which does mean the four-state chain reads Draft → Pending → Approved/Returned rather than having a separate "Submitted" state. Liquidations keep their own draft/submitted pair.
  • Untouched from before, still true: Render's free tier blocks outbound SMTP, so email-change notifications will not reach an arbitrary inbox on the deployed site; and VITE_SHOW_QA_CREDS=true is still live on public production.
